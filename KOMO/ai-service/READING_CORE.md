# 文档阅读核心

2026-10-22更新。主线是“用户导入/编辑文档 → 围绕原文与AI讨论 → 核对原文 → 用户自行完善文档”。新阅读路径不创建草稿，不修改文章，也不触发跨知识库检索。普通聊天与长文阅读使用Python混合检索，详见[检索架构](RETRIEVAL.md)。

## 运行与边界

- `app/reading/core.py`：无第三方依赖、无凭证、无网络。文档切分、词法取段、上下文预算、引用编号检查。
- `app/reading/runtime.py`：注入生成、取证决策与检索适配器；每个Python进程最多4个阅读请求，等候容量2秒，总执行超时90秒，输出最多24000字符。长文在最终生成前运行有限工具循环，短文全文输入时跳过额外决策。
- `app/reading/agent.py`：只读取证工具、参数校验、两轮预算、原文装载与运行轨迹。工具范围绑定当前文档快照，模型参数不接受用户ID、文档ID、URL或文件路径。
- `app/api/reading.py`：`POST /api/reading/sync`与`/stream`。适配现有模型，生成上限2048 tokens。内部接口只接收Java已校验归属的文档快照，不接受客户端传入权限范围。接口同时要求AI_INTERNAL_TOKEN；部署必须继续只允许业务服务访问AI端口。
- Java `ReadingConversationService`：按当前用户校验会话和文章，获取最近20条消息，再保存用户消息并调用AI；模型调用不在数据库事务内。返回证据必须与发送的文档哈希和原文切片一致。只有收到完成标志与完整上下文才保存AI回复。
- `Message.readingContext`：保存本轮文档哈希、证据原文、行号、覆盖范围、运行ID和引用检查结果。它是回答的证据快照，不是完整文档版本库。
- Web阅读面板：实时展示并可展开原文片段；文档改变后保留回答时的片段并提示版本不同。编辑仍通过原有编辑页面，由用户操作。

当前是单文档只读阅读Agent：长文可自主选择搜索、目录和章节工具，最后一次调用生成答案。长文已接入embedding与BM25混合检索；普通聊天支持知识库范围检索。没有持久Agent运行队列、生成进程崩溃后续跑、自动文档写入或全量版本历史。工具循环已做离线与有限真实请求验证；补读作为当前产品决策保留，优先完善端到端可用性，不以证明学习收益作为交付前提。

## 文档策略

短文在12000字符以内优先全文输入；长文按Markdown标题、长度切段，生产路径使用BM25与本地embedding融合。选区优先；在前12个候选涉及的章节中，为章节/父章节导言分配最多一半上下文，再放入命中和相邻片段，避免同一章节的大量代码挤掉能力限制。纯函数保留词法基线供对照。最终最多24个片段、合计12000字符；最多4096个候选片段，超过则明确失败，不偷偷截断。代码围栏中的`#`不作为Markdown标题。

字符预算不是精确token预算。历史最多12条、合计8000字符；单个历史消息超预算时保留较新的完整消息，不切掉句子的一半。当前仅拼接最近两条用户问题辅助追问，不做历史摘要或模型查询改写，指代/同义表达与长文全局总结仍可能失败。这些属于能力边界，不阻塞当前阅读问答闭环交付。

选区从消息开头的Markdown引用读取。找不到、重复出现或超出片段预算时分别报告，不能把不确定位置当成精确定位。引用使用`[S1]`等本轮编号；程序只校验编号是否存在和证据是否来自原文，**不证明引用支持结论或内容事实正确**。缺少引用仍会提示；无效编号现在使本轮失败，不再完成或保存为成功回答。流式输出中可能已经显示部分文本，仍以错误事件标记未完成。

资料通过用户数据消息传入，不能成为system指令；模型只有当前文档只读工具，没有修改文章、联网或执行代码的工具。提示词分层并不保证模型永不受文档中的恶意指令影响，相关行为仍需真实模型评测。

## 有限取证循环（2026-10-22）

1. 初次检索后，模型查看证据和分页目录，自主选择`search_document(query)`、`read_section(start_chunk)`、`list_sections(start_chunk)`，或不调用工具停止。检索使用同一用户和文档版本的混合引擎。
2. 默认最多两轮决策、每轮三个工具。Runtime的max_rounds参数允许0—3，用于预算配置和对照测评，0关闭补读；不是客户端可传入的权限字段。单次正文结果最多4800字符，累计最多12000字符；目录每次最多20项/2000标题字符。工具结果含块编号、原文位置、继续读取位置，不用模型摘要冒充原文。
3. 重复调用不重复执行；未知工具、非法参数、重复调用ID、超量调用或工具故障明确失败。最多30秒用于取证，并在总90秒预算内尽量留15秒给最终生成；取证预算耗尽可带限制继续回答，真实检索故障不会伪装成预算耗尽。
4. 最终保留选区优先，并为初始证据中的章节导言预留最多6000字符，再放入补读证据和剩余初始证据，仍受12000字符/24片段上限约束。这是结构性保护，不是识别所有语义条件。被舍弃的初始块、补读块分别记录为`omitted_initial_chunks`和`omitted_read_chunks`；选区等竞争导致保护块未放入时另记`omitted_protected_chunks`。证据重新编号，最终生成只接收这组证据，不携带取证模型的自由文本和工具历史。原文仍由Java核验哈希及字符位置。
5. `readingContext.agent`记录轮数、工具名、参数、返回块编号、保留/遗漏块、读入字符数、耗时和停止原因。状态在生成token之前更新并随完成回复存储；不是思维链或事实认证。

取证使用现有DeepSeek模型的原生tool calls，关闭thinking模式，每次最多768输出tokens且无SDK重试；最终生成也显式关闭thinking，仍最多2048输出tokens、最多一次SDK重试。参考[提供方工具协议](https://api-docs.deepseek.com/guides/tool_calls/)。最坏每题两次取证调用加一次生成调用（生成可能重试），比原单次生成有额外成本和延迟。正常结束标记缺失、截断、内容过滤均不能作为完成。

这版只做取证、引用编号与原文真实性约束。语义支持性、条件理解和补充解释是否正确依然需要人工/真实模型测评；没有声称模型已能判断真伪，也没有完整MDX渲染/语言分支解析。

2026-10-22真实模型补充验证已完成，详见[轮数对照与缺陷](evals/agent-learning/results/AGENT_ROUNDS_FINDINGS.md)。5题×0/1/2轮共30次请求，一轮补读补齐a02/a15的关键依据，第二轮在这5题均只确认停止。15份回答中5份因输出上限截断，且u02补读挤掉了初始能力条件。这组记录用于定位缺陷，不再继续轮数收益实验。最终生成thinking预算及证据淘汰已在后续修复，见下方记录；语义正确性不能由这组结果保证。

## 独立评测

在`KOMO/ai-service`目录运行，Python 3.12：

```bash
python -m unittest discover -s tests -p test_reading_core.py
python -m app.reading.evaluate evals/reading/cases.jsonl --output reading-report.json
```

以上评测默认不导入模型配置，不需要登录、API密钥、Java、PG、ES或MQ。JSONL每行格式：

```json
{"id":"q1","category":"conditions","document":{"id":"doc1","title":"文档标题","content":"原文"},"question":"实际问题","selection":"","history":[],"required_evidence":["必要的原文依据"],"expected_behavior":"人工判断标准"}
```

报告记录文档哈希、策略版本、覆盖范围、必要证据进入上下文的数量，以及旧12000字符前缀基线的数量。对“无答案”等任务不应制造必要依据，使用`expected_behavior`交给人工判断。

`evals/reading/cases.jsonl`只有8个合成诊断样例，覆盖短文、条件、长文尾部、选区、无答案、精确术语、追问和恶意资料。它们不是用户的真实语料，也不足以证明检索方案优劣。应补充实际使用问题，并划分调试集和保留测试集。

显式加入`--generate`才调用配置的真实模型并产生费用：

```bash
python -m app.reading.evaluate evals/reading/cases.jsonl --generate --output reading-generated.json
```

该模式复用产品runtime，记录模型、回答、延迟与引用编号检查。回答是否准确、限定条件是否遗漏、引用是否支持结论、无答案是否诚实仍需人工标注。不要把字符串命中率称为回答准确率。

## 草稿暂停与接入

Java新增`komo.extraction.enabled`，对应`EXTRACTION_ENABLED`，默认为`false`。关闭时自动入队不执行，手动提取明确拒绝，Rabbit listener不自动启动；现有用户的`autoExtract=true`也不会覆盖此部署开关。历史草稿、原始队列消息和确认/驳回接口保留，不清空数据。设置页保留历史草稿入口，主导航、聊天操作和新手流程不再引导提取。旧处理器保留用于兼容与后续数据处置，并非本轮删除数据表。

新Java、Python和前端需要配套更新。旧Python没有`/api/reading`时会明确报错，不回退到未标注依据的旧阅读提示词。

`messages.reading_context`为新增可空TEXT字段。遵循项目现有schema策略：本地`ddl-auto=update`可添加字段；生产若为`validate`，需要先走项目的schema变更流程，不能直接把生产改成`update`。本轮没有迁移生产库或部署服务器。

## 当前交付标准（2026-10-22产品决策）

保留有限补读，目标是给用户一个方便、可核查的文档问答渠道。工程回归用于防止流程损坏，不再以证明Agent优于其他方式或学习效果提升作为开发前置条件。

本轮修复前端消息生命周期：文章/会话按ID隔离组件状态，旧请求不覆盖新会话；聊天页与阅读面板共用同步逻辑；以SSE完成事件中的消息ID核对落库结果，不再用拉取时间及最后一条角色推测；上一轮的迟到同步不能清理新一轮流。完成事件到达即可释放连接，不等待代理关闭HTTP。历史同步失败保留已生成回答并提示重新加载；会话初始化失败可重试；中文输入法确认选词不会发送问题。

本轮73项前端自动测试通过（新增13项消息同步回归），Next.js生产构建通过。首次构建因沙箱创建输出目录报EPERM，外部执行同一构建成功；没有追加真实模型调用。验证范围不等同于实际部署、真实数据库/模型的全链路验收。浏览器刷新会丢失未保存的部分回答，服务端仍会尝试完成有时限的请求；生成进程崩溃后续跑及请求幂等重试仍未实现。
